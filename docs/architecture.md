# Архитектура приложения

В проекте используется **Clean Architecture** с разделением по функциональным блокам (**Feature**).
Общие компоненты приложения находятся `core`.
Каждая Feature отвечает за собственную функциональность.
Правила организации кода и взаимодействия между разработчиками описаны в `architecture.md` и `CONTRIBUTING.md`.

---

## 1. Структура проекта

| Feature     | Назначение                               |
|-------------|------------------------------------------|
| `search`    | Поиск вакансий                           |
| `vacancy`   | Просмотр подробной информации о вакансии |
| `favorites` | Работа со списком избранных вакансий     |
| `filter`    | Фильтрация вакансий                      |
| `team`      | Информация о команде                     |

Каждая Feature содержит слои `data`, `domain`, `presentation` и папку `di` для Koin.

Структура Feature:
```text
<feature>/
    data/
        repository/
        dto/
        entity/
        mapper/
        api/
        database/
    domain/
        models/
        repository/
        interactor/
    presentation/
        model/
        mapper/
        ui/
        state/
        viewmodel/
    di/
        <name>Module.kt
```
> Используется единая структура. Дополнительные папки и файлы создаются по мере необходимости.
> Общие компоненты приложения размещаются в `core` (см. раздел 2)

## 2. Общие компоненты (Core)

| Папка          | Назначение                       | Содержимое                                                        |
|----------------|----------------------------------|-------------------------------------------------------------------|
| `network`      | Работа с сетью                   | Retrofit, OkHttp, сетевой клиент                                  |
| `database`     | Работа с базой данных            | Создание Room Database, общая конфигурация и общие настройки      |
| `designsystem` | Общий стиль приложения           | Цвета, темы, типографика, размеры, UI-компоненты                  |
| `navigation`   | Навигация между экранами         | Общие интерфейсы, маршруты и вспомогательные компоненты навигации |
| `common`       | Общие вспомогательные компоненты | Result-обёртки, extensions, хелперы. Без бизнес-логики            |
| `di`           | Общие зависимости                | Общие Koin-модули                                                 |

Правила размещения в `core`:

- В `core` размещаются только компоненты, необходимые нескольким Feature.
- Если компонент нужен только одной Feature, он остаётся в этой Feature.
- Если компонент перестал быть общим, его можно вернуть в соответствующую Feature.
- В `core/designsystem` выносятся общие UI-компоненты, которые являются частью единой дизайн-системы приложения.
- Компоненты, специфичные для конкретной Feature, остаются в `presentation/ui` этой Feature.
- В `core/common` размещаются только общие технические компоненты.
- `core` не зависит от отдельных Feature.

Общие настройки и инфраструктура находятся в `core`, а конкретные источники данных - в соответствующей Feature

Например:
```text
core/network - настройка Retrofit и OkHttp.
search/data/api - API-интерфейсы поиска.
core/database - создание и настройка Room Database.
favorites/data/database - DAO и локальные источники данных избранного.
```

## 3. Правила работы со слоями

### Data
Назначение: получение данных из внешних источников, работа с локальным хранилищем, преобразование DTO и Entity в Domain-модели, реализация контрактов Domain.

Правила:
- `repository` - реализации интерфейсов из `domain/repository`.
- `dto` - модели сетевых запросов и ответов.
- `entity` - модели базы данных Room.
- `mapper` - преобразование DTO и Entity в Domain-модели.
- `api` - сетевые интерфейсы конкретной Feature.
- `database` -  DAO и локальные источники данных конкретной Feature.
- Общие настройки Retrofit, OkHttp, Room - в `core`.
- Репозитории скрывают от Domain особенности получения и хранения данных.
- Ошибки API и базы данных обрабатываются в Data и при необходимости преобразуются в понятные для Domain результаты.
- Для асинхронных операций используются Kotlin Coroutines.
- suspend применяется для разовых операций, Flow - для наблюдения за изменяющимися данными.
- Репозитории отвечают за выполнение операций в подходящем Dispatcher, чтобы тяжёлые операции не выполнялись на Main Thread.

### Domain
Назначение: бизнес-правила, модели предметной области, контракты получения данных.

Правила:
- `models` - модели предметной области.
- `repository` - интерфейсы репозиториев.
- `interactor` - классы с бизнес-логикой, выполняющие отдельные операции приложения.
- Интерфейсы Interactor создаются при необходимости, а не для каждой операции автоматически.
- Реализации интеракторов размещаются в `domain`, не используют Android SDK и обращаются к данным только через интерфейсы репозиториев.
- Domain не зависит от `data`, `presentation`, Android Framework и конкретных технологий получения и хранения данных.
- Domain не использует DTO, Entity, API-интерфейсы и DAO.

### Presentation
Назначение: подготовка и отображение данных, обработка действий пользователя, управление состоянием экрана.

Правила:
- `viewmodel` - состояние экрана и обработка действий; не содержит бизнес-логику.
- `state` - модели состояния экрана (UI State).
- `model` - UI-модели.
- `mapper` - преобразование Domain-моделей в UI-модели.
- `ui`- Composable-компоненты и экраны Feature.
- ViewModel взаимодействует с Domain через Interactor.
- ViewModel формирует UI State, а UI наблюдает за ним и отображает актуальное состояние.
- Пользовательские действия передаются из UI во ViewModel.
- Для хранения UI State необходимо использовать StateFlow.
- Локальное состояние интерфейса, не требующее управления на уровне экрана, может храниться внутри Composable.
- Presentation отвечает за отображение ошибок пользователю.
- UI не должен самостоятельно обрабатывать технические ошибки Retrofit или Room.
- UI не обращается напрямую к Retrofit, Room или реализациям репозиториев.

### DI

Назначение: создание и связывание зависимостей внутри Feature; общие зависимости - в `core/di`.

Правила:
- Koin-модуль каждой Feature располагается в `<feature>/di`.
- Общие зависимости приложения регистрируются в `core/di`.
- Регистрируются ViewModel, реализации Interactor и реализации Repository.
- Интерфейсы Repository связываются с реализациями из Data.
- При наличии интерфейсов Interactor они также связываются с соответствующими реализациями.
- DI-модули подключают необходимые зависимости из Core.
- DI не содержит бизнес-логику.

## 4. Правила зависимостей

### Направление зависимостей
Зависимости между слоями направлены к слою `domain`
Это означает, что Presentation и Data зависят от Domain, но не зависят друг от друга напрямую.
```text
Presentation -> Domain <- Data
                    ▲
                    │ (интерфейсы domain)
                  DI -> связывает интерфейсы и реализации,
                         подключает core/di
 ```

- `presentation` зависит от `domain` и использует его модели и Interactor.
- `data` зависит от `domain` и реализует объявленные в нём интерфейсы репозиториев.
- `domain` не зависит от других слоёв и содержит основную бизнес-логику.
- `core` не зависит от Feature, но Feature может использовать компоненты `core`.
- Feature не обращается к внутренним классам другой Feature.
- UI не обращается к API, БД или реализациям репозиториев.
- DI связывает интерфейсы с реализациями и не содержит бизнес-логики.

> **Главное правило:** бизнес-логика не должна зависеть от того, как именно получаются, хранятся или отображаются
> данные.

## 5. Взаимодействие между Feature

- Каждая Feature отвечает за собственную функциональность.
- Feature не обращается напрямую к внутренним классам другой Feature.
- Общие компоненты и общие модели размещаются в `core`.
- Одинаковая логика нескольких Feature выносится в core после согласования командой.
- Переходы между экранами выполняются через общую инфраструктуру `core/navigation`.
- Каждая Feature самостоятельно описывает свои маршруты и экраны.
- Объединение навигационных графов Feature выполняется на уровне приложения, а не внутри `core`.
- Для передачи данных между экранами используются необходимые идентификаторы и аргументы навигации, а не внутренние объекты другой Feature.
- Циклические зависимости между Feature запрещены.

## 6. Внедрение зависимостей (Koin)

Для внедрения зависимостей используется библиотека **Koin**. 
У каждой Feature собственный DI-модуль в `<feature>/di`. Общие зависимости приложения регистрируются в `core/di`.

1. Каждый участник изменяет только DI-модуль своей Feature.
2. Общие зависимости, требующие внедрения, например сетевой клиент и база данных, регистрируются в `core/di` и не дублируются в модулях Feature.
3. ViewModel регистрируются через `viewModel {}`.
4. Repository обычно регистрируются через `single {}`.
5. Для Interactor используется `single {}` или `factory {}` в зависимости от необходимости создания нового экземпляра.
6. Все DI-модули подключаются в `App.kt`. Список всех модулей формируется на начальном этапе проекта (Epic 0).
7. На начальном этапе DI-модули Feature могут быть пустыми.
8. После завершения Epic 0 `App.kt` изменяется только через отдельный согласованный PR.

### Подключение модулей в App.kt

Все модули регистрируются в `startKoin`:

```kotlin
startKoin {
    androidContext(this@App)
    modules(
        networkModule,
        // databaseModule, searchModule и др. по необходимости
    )
}
```

## 7. Правила изменения

- Каждый разработчик изменяет только модуль своей Feature.
- Изменения, затрагивающие несколько Feature, и изменения общих контрактов domain (интерфейсов репозиториев/интеракторов) предварительно согласуются командой и изменяются через отдельный PR.
- Добавление новых общих компонентов или изменение существующих компонентов Core выполняется через отдельный согласованный PR.
- Все Koin-модули создаются и регистрируются в `App.kt` на старте проекта.
- `App.kt` после старта проекта изменяется только через отдельный согласованный PR.
